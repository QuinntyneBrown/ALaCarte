# L2 - Detailed Requirements

## Traceability

Each requirement traces to an L1 requirement using the format **[L1-N]**.

---

## 1. Multi-Repository Composition [L1-1]

### 1.1 Git Repository Initialization

The system shall create a new Git repository in the target workspace folder to serve as the composition root.

**Acceptance Criteria:**
- A `.git` directory is created in the workspace root via `git init`.
- The workspace folder must not already exist; the system shall fail with a validation error if it does.

### 1.2 Submodule-Based Repository Integration

The system shall add each source repository as a Git submodule under a configurable subdirectory.

**Acceptance Criteria:**
- Each repository URL provided via `--repos` is added as a submodule under `{SubmodulesFolderName}/` (default: `submodules/`).
- The submodule is checked out on the branch specified by `--branch` (default: `main`).
- HTTPS URLs (e.g., `https://github.com/org/repo.git`) are accepted.
- SSH URLs (e.g., `git@github.com:org/repo.git`) are accepted, including custom hosts and nested paths.
- If a submodule addition fails, the system logs a warning and continues processing remaining repositories.

### 1.3 Repository Name Extraction

The system shall derive a human-readable repository name from the provided URL for use as the submodule directory name.

**Acceptance Criteria:**
- For HTTPS URLs, the last segment of the URI path is used (e.g., `https://github.com/org/my-project.git` yields `my-project`).
- For SSH URLs, the portion after `:` is parsed and the last path segment is used (e.g., `git@github.com:group/subgroup/repo.git` yields `repo`).
- The `.git` suffix is stripped from all extracted names.

## 2. Selective Project Inclusion [L1-2]

### 2.1 Project Filtering via CLI

The system shall accept an optional `--projects` argument to restrict which projects are included in the composed workspace.

**Acceptance Criteria:**
- When `--projects` is omitted, all discovered projects are included.
- When `--projects` is provided, only projects matching at least one filter are included.
- Filters apply to both .NET and Angular project discovery.

### 2.2 Filter Matching Rules

The system shall support exact name matching, wildcard patterns, and path containment for project filters.

**Acceptance Criteria:**
- Exact name match is case-insensitive (e.g., `ProjectA` matches `ProjectA.csproj`).
- Wildcard `*` matches any characters within a single path segment (e.g., `test*` matches `testing`).
- Wildcard `**` matches across path separators (e.g., `**/ConferenceEventManager/*` matches nested paths).
- Wildcard `?` matches a single character.
- Path containment: a filter matches if it appears anywhere in the project's relative path.

## 3. Automatic Dependency Resolution [L1-3]

### 3.1 NuGet-to-ProjectReference Replacement

The system shall detect when a `PackageReference` in a `.csproj` file refers to a package whose source project is present in the workspace, and replace it with a `ProjectReference`.

**Acceptance Criteria:**
- The system reads the `PackageId` element from each discovered `.csproj` file and builds a mapping of package ID to project file path.
- For each `PackageReference` whose `Include` attribute matches a known `PackageId`, the element is removed and a `ProjectReference` with the correct relative path is inserted.
- The `ItemGroup` for `ProjectReference` elements is created if it does not exist.
- Projects that do not match any known `PackageId` retain their original `PackageReference` unchanged.

### 3.2 Relative Reference Stripping

The system shall remove file references that point outside the project directory, since those paths are invalid after copying.

**Acceptance Criteria:**
- `Reference` elements with paths starting with `..` are removed.
- `Compile`, `Content`, and `None` item elements with relative paths pointing outside the project are removed.
- Absolute and local references are preserved.

## 4. Technology-Agnostic Integration [L1-4]

### 4.1 .NET Project Discovery

The system shall discover all .NET projects within the submodule directory tree.

**Acceptance Criteria:**
- All `*.csproj` files are found recursively under the submodules directory.
- Files within `obj/` and `bin/` directories are excluded.
- Discovered project paths are returned as absolute paths.

### 4.2 .NET Solution Creation

The system shall generate a `.sln` file containing all discovered (and optionally filtered) .NET projects.

**Acceptance Criteria:**
- A solution file is created via `dotnet new sln -n {SolutionName}` (default name: `Solution`).
- Each project is copied to `src/{ProjectName}/` with `obj/` and `bin/` directories excluded from the copy.
- Each copied project is added to the solution via `dotnet sln add`.
- If no .NET projects are discovered, solution creation is skipped entirely.

### 4.3 Angular Project Discovery

The system shall discover Angular workspaces by locating `angular.json` files within the submodule directory tree.

**Acceptance Criteria:**
- All `angular.json` files are found recursively under the submodules directory.
- Files within `node_modules/` and `dist/` directories are excluded.
- Each `angular.json` is parsed to extract the list of project names, root paths, and project types.

### 4.4 Angular Workspace Creation

The system shall generate a unified Angular workspace containing all discovered Angular projects.

**Acceptance Criteria:**
- A new Angular workspace is created via `ng new {WorkspaceFolderName} --skip-git --create-application=false` (default folder name: `Ui`) under `src/`.
- Each Angular project directory is copied to `{workspace}/projects/{projectName}/`, excluding `node_modules/` and `dist/`.
- The generated `angular.json` is updated to merge project configurations from all source workspaces, with `root` paths rewritten to `projects/{projectName}` and `sourceRoot` to `projects/{projectName}/src`.
- If the Angular CLI is not installed and `AutoInstallCli` is `true`, the system installs it via `npm install -g @angular/cli` before proceeding.
- If the Angular CLI is not installed and `AutoInstallCli` is `false`, the system logs a warning and creates an empty workspace folder without failing.
- If no Angular projects are discovered, workspace creation is skipped entirely.

### 4.5 Extensibility

The system architecture shall support adding new technology integrations without modifying existing services.

**Acceptance Criteria:**
- Each technology stack (Git, .NET, Angular) is encapsulated behind a dedicated service interface (`IGitService`, `IDotNetService`, `IAngularService`).
- New technology services can be registered in the DI container without modifying existing service implementations.
- The `IProjectDiscoveryService` interface provides a pattern for adding discovery methods for new technology stacks.

## 5. Source Repository Preservation [L1-5]

### 5.1 Submodule Traceability

The system shall maintain a link from the composed workspace back to each source repository via Git submodules.

**Acceptance Criteria:**
- Each source repository remains a fully functional Git submodule under `{SubmodulesFolderName}/`, retaining its `.git` metadata and remote configuration.
- The workspace root `.gitmodules` file records the URL and branch of each source repository.
- The original source repositories are never modified during composition.

### 5.2 Copied Project Attribution

Copied project files within `src/` shall be traceable to their source submodule.

**Acceptance Criteria:**
- The directory structure under `src/` preserves the original project name, allowing correlation with the corresponding submodule project.
- The submodule directory retains the unmodified original source for reference and diffing.

---

## 6. Bidirectional Synchronization [L1-6]

### 6.1 Upstream Pull Support

The system shall support pulling upstream changes from source repositories into the workspace.

**Acceptance Criteria:**
- Because source repositories are Git submodules, standard `git submodule update --remote` retrieves upstream changes.
- The workspace Git repository tracks the submodule commit references, making updates reproducible.

### 6.2 Downstream Push Support

The system shall support pushing local changes made within submodules back to their source repositories.

**Acceptance Criteria:**
- Each submodule retains its remote configuration, enabling `git push` from within the submodule directory.
- Changes committed within a submodule directory are attributed to that submodule's repository history, not the workspace root.

---

## 7. Reproducible Workspaces [L1-7]

### 7.1 Deterministic Configuration

The system shall use a configuration file to define all workspace creation parameters with sensible defaults.

**Acceptance Criteria:**
- Configuration is loaded from `appsettings.json` at the CLI root.
- The following settings are configurable: `DefaultBranch`, `SubmodulesFolderName`, `SourceFolderName`, `SolutionName`, `WorkspaceFolderName`, `AutoInstallCli`, `ExcludedDirectories` (for both .NET and Angular), `ExecutablePath` (for git and dotnet), and `TimeoutSeconds` for Git operations.
- All settings have documented defaults: branch=`main`, submodules folder=`submodules`, source folder=`src`, solution name=`Solution`, Angular workspace=`Ui`, auto-install CLI=`true`, excluded .NET dirs=`[obj, bin]`, excluded Angular dirs=`[node_modules, dist]`, git timeout=`300s`.

### 7.2 CLI Reproducibility

The same CLI invocation with the same arguments and source repository state shall produce a structurally identical workspace.

**Acceptance Criteria:**
- Given identical `--repos`, `--branch`, `--projects`, and `--folder` arguments, the resulting workspace contains the same submodules, projects, solution structure, and dependency rewiring.
- The workspace folder name can be specified via `--folder` or auto-generated if omitted.

---

## 8. Non-Destructive Operation [L1-8]

### 8.1 Workspace Isolation

All composition operations shall occur within a newly created workspace directory, leaving source repositories unmodified.

**Acceptance Criteria:**
- The system creates a new directory for the workspace; it does not write to any existing directory.
- If the specified folder already exists, the system fails with a validation error rather than overwriting.
- Source repositories are added as submodules (read-only clone), not modified in place.

### 8.2 Project Copy Semantics

Projects included in the workspace are copies, not symlinks or in-place modifications.

**Acceptance Criteria:**
- .NET projects are copied from `submodules/{repo}/` to `src/{ProjectName}/`, producing independent copies.
- Angular projects are copied from their source workspace to `src/{WorkspaceFolderName}/projects/{projectName}/`, producing independent copies.
- Modifications to copied projects (e.g., dependency rewiring) do not affect the original files in the submodule directories.

### 8.3 Graceful Error Handling

The system shall handle errors without leaving partial or corrupted state in source repositories.

**Acceptance Criteria:**
- `OperationCanceledException` is caught and the system exits with code 1 and a warning log.
- Unexpected exceptions are caught and the system exits with code 1 and an error log including the exception message.
- Individual submodule failures do not abort the entire operation; the system warns and continues.
- Process execution failures for `git`, `dotnet`, and `ng` commands raise typed exceptions (`GitOperationException`, `DotNetOperationException`, `AngularOperationException`) with the command, exit code, and standard error captured.
